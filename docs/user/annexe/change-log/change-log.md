## Historique des versions de l'application

### Version 0.3.0 - 14 octobre 2026

**Nouvelles fonctionnalités**

- **Tickets — Filtre par statut sur la liste** : `GET /api/tickets` accepte un paramètre de requête optionnel `status` et ne renvoie alors que les tickets de ce statut, du plus récent au plus ancien.
  - `GET /api/tickets?status=<valeur>` avec `<valeur>` parmi `open`, `in_progress`, `closed` (comparaison exacte, sensible à la casse) renvoie `200` avec `items` limité aux tickets de ce statut, triés par `createdAt` DESC puis `id` DESC, et `count` égal au nombre d'éléments ; sans correspondance, la réponse est `200` `{"items": [], "count": 0}`.
  - Toute valeur `status` présente mais inconnue (chaîne vide, `Open`, `OPEN`, `%20open`, `done`, ou une valeur non scalaire comme `status[]=open`) renvoie `400` en `application/json` avec exactement `{"error": "Invalid status", "allowed": ["open", "in_progress", "closed"]}` ; la liste `allowed` reflète `Ticket::STATUSES` dans son ordre de déclaration. La base n'est pas interrogée dans ce cas et aucune page HTML d'erreur n'est produite.
  - Sans paramètre `status`, le comportement est inchangé : tous les tickets, même ordre, même enveloppe `items` / `count`, même objet ticket (`id`, `title`, `description`, `priority`, `status`, `createdAt`, `dueAt`, `assignee`). `POST /api/tickets`, `GET /api/tickets/{id}`, `PATCH /api/tickets/{id}/status` (toujours `422` sur statut invalide) et `GET /api/stats` ne sont pas modifiés.
  - Dépôt `App\Repository\TicketRepository` : nouvelles méthodes `createNewestFirstQueryBuilder()` (alias `t`, tri `createdAt` DESC, `id` DESC, sans clause `WHERE`), `withStatus(QueryBuilder, string)` (ajoute `AND t.status = :status` via `andWhere`, empilable avec d'autres filtres) et `findNewestFirst(?string $status = null)` ; `findAllNewestFirst()` conserve son nom et son résultat en déléguant à `findNewestFirst()`, `countByStatus()` est inchangé.
  - **Impact API** : nouveau code de réponse `400` (`application/json`, corps `error` + `allowed`) sur `GET /api/tickets` lorsque `status` est fourni avec une valeur invalide ; auparavant ce paramètre était ignoré et la liste complète renvoyée en `200`. Aucun changement de forme pour les réponses `200`.
- **Agents — Création et liste des agents** : deux nouveaux endpoints, `POST /api/agents` pour créer un agent (e-mail unique) et `GET /api/agents` pour lister les agents, actifs en premier.
  - `POST /api/agents` reçoit un objet JSON `{"name": string, "email": string, "active"?: bool}` avec `Content-Type: application/json` et renvoie `201` avec l'objet agent `{"id", "name", "email", "active"}` (clés dans cet ordre, aucune autre clé, pas d'en-tête `Location`). `active` vaut `true` par défaut ; `name` et `email` sont stockés tels quels (ni rognage ni passage en minuscules) ; les clés inconnues du corps sont ignorées.
  - Validation (`422`, `application/json`, corps `{"errors": {"<champ>": "<message>"}}`, un message par champ en faute, premier message de violation) : `name` obligatoire, non vide après `trim`, 120 caractères maximum ; `email` obligatoire, non vide après `trim`, adresse syntaxiquement valide, 180 caractères maximum ; `active` doit être un booléen s'il est fourni. Rien n'est persisté dans ces cas. Les messages par défaut de Symfony sont en anglais (aucun traducteur installé).
  - Unicité de l'e-mail : un `email` déjà présent (comparaison exacte, sensible à la casse, comme l'index unique) renvoie `422` avec exactement `{"errors": {"email": "An agent with this email already exists."}}` ; le contrôle passe par `AgentRepository::findOneBy(['email' => ...])` avant l'insertion, et une `UniqueConstraintViolationException` au `flush()` (insertion concurrente) est rattrapée et renvoie le même corps `422`, jamais un `500`.
  - Corps non JSON ou vide : `400` ; `Content-Type` autre que JSON (par exemple `text/plain`) : `415` (`#[MapRequestPayload(acceptFormat: 'json')]`). Dans les deux cas la réponse est en `application/json` avec `{"error": "<message>"}`.
  - `GET /api/agents` renvoie `200` et `{"items": [<agent>, ...], "count": n}`, `count` égal au nombre d'éléments ; tri `active` DESC puis `id` ASC (agents actifs d'abord, chaque groupe par ordre de création) ; sans agent, exactement `{"items": [], "count": 0}`. Les paramètres de requête sont ignorés (ni filtre ni pagination).
  - Dépôt `App\Repository\AgentRepository` : nouvelle méthode `findActiveFirst(): list<Agent>` (`findBy([], ['active' => 'DESC', 'id' => 'ASC'])`). Nouveaux fichiers `src/Controller/AgentController.php` (routes `agent_list`, `agent_create`), `src/Dto/CreateAgentRequest.php` (DTO `final readonly`, contraintes `#[Assert\...]`) et `src/EventListener/ApiExceptionListener.php`. Aucune migration ; l'entité `Agent` et le schéma sont inchangés.
  - Rendu JSON des erreurs HTTP sous `/api/` : l'écouteur `ApiExceptionListener` (`KernelEvents::EXCEPTION`) convertit en JSON toute exception `HttpExceptionInterface` levée pour un chemin commençant par `/api/` (`{"errors": {...}}` si l'exception enveloppe une `ValidationFailedException`, `{"error": "<message>"}` sinon, code de statut et en-têtes de l'exception conservés). Les autres exceptions ne sont pas touchées et les réponses construites par les contrôleurs ne sont pas modifiées.
  - Dépendances : `symfony/property-access` et `symfony/property-info` ajoutés à `composer.json` (requis par `#[MapRequestPayload]` sur un DTO) ; recette Flex `config/packages/property_info.yaml` (`framework.property_info.with_constructor_extractor: true`).
  - Appelants existants : `GET/POST /api/tickets`, `GET /api/tickets/{id}`, `PATCH /api/tickets/{id}/status` (toujours `422` `{"error": "Invalid status"}` sur statut invalide) et `GET /api/stats` conservent leurs codes de statut et leurs corps JSON.
  - **Impact API** : deux nouvelles routes `GET /api/agents` (`200`) et `POST /api/agents` (`201`, `400`, `415`, `422`). Effet de bord de l'écouteur : une route inconnue sous `/api/` renvoie désormais son `404` en `application/json` `{"error": "<message>"}` au lieu de la page HTML d'erreur du noyau ; aucun code de statut ni forme de réponse des endpoints existants ne change.
- **Agents — Activation et désactivation d'un agent** : nouvel endpoint `PATCH /api/agents/{id}` pour changer le drapeau `active` d'un agent existant, seule modification possible après sa création ; chaque changement est journalisé.
  - `PATCH /api/agents/{id}` (route `agent_active`, `id` numérique) reçoit un objet JSON `{"active": bool}` avec `Content-Type: application/json` et renvoie `200` avec l'objet agent complet `{"id", "name", "email", "active"}` (clés dans cet ordre, aucune autre clé) après modification. `name` et `email` ne sont jamais modifiés par cet endpoint ; les clés inconnues du corps (`name`, `email`, `id` compris) sont ignorées. Envoyer la valeur déjà en place est accepté (`200`, même corps).
  - La valeur est persistée : `GET /api/agents` reflète immédiatement le nouveau drapeau et son tri (actifs d'abord, puis `id` croissant). Désactiver un agent ne retire pas ses affectations : les tickets qui lui sont affectés le restent.
  - Validation (`422`, `application/json`, corps `{"errors": {"active": "<message>"}}`, `active` seule clé de `errors`) : clé `active` absente (`{}` ou autres clés seulement), `null`, chaîne (`"yes"`, `"true"`, `""`), nombre (`1`, `0`) ou tableau. L'agent n'est pas modifié dans ces cas. Le corps est validé avant la recherche de l'agent : un `id` inconnu avec un corps invalide renvoie `422`, pas `404`.
  - `id` numérique sans agent correspondant : `404` avec exactement `{"error": "Agent not found"}`. `id` non numérique (`/api/agents/abc`) : `404` `{"error": "<message>"}` (requirement `\d+` de la route). `GET /api/agents/{id}` : `405` `{"error": "<message>"}` avec un en-tête `Allow` contenant `PATCH`. Corps non JSON ou vide : `400` ; `Content-Type` autre que JSON : `415` (`#[MapRequestPayload(acceptFormat: 'json')]`). Toutes ces erreurs sont en `application/json`, rendues par `ApiExceptionListener` existant.
  - Journalisation : chaque `200` (y compris sans changement de valeur) écrit, après le `flush()`, exactement une ligne `info` `Agent activation changed` avec le contexte `{"id": <id agent>, "active": <nouvelle valeur>}` ; les réponses `400`, `404`, `415` et `422` ne sont pas journalisées.
  - Nouveau fichier `src/Dto/UpdateAgentActiveRequest.php` (DTO `final readonly`, propriété `?bool $active = null` avec `#[Assert\NotNull]` ; la valeur par défaut `null` fait qu'une clé manquante est refusée au lieu d'activer silencieusement l'agent) ; `AgentController` gagne l'action `changeActive()`, ses actions `list` et `create` et son constructeur sont inchangés. Aucune migration, aucun changement de schéma, aucune dépendance ni configuration ajoutée ; `Agent`, `AgentRepository`, `ApiExceptionListener` et `TicketController` ne sont pas modifiés.
  - Appelants existants : `GET /api/agents`, `POST /api/agents` (y compris ses corps `422` et le message d'e-mail en doublon), `GET/POST /api/tickets`, `GET /api/tickets/{id}`, `PATCH /api/tickets/{id}/status` et `GET /api/stats` conservent leurs codes de statut et leurs corps JSON.
  - **Impact API** : nouvelle route `PATCH /api/agents/{id}` (`200`, `400`, `404`, `415`, `422`) et, par conséquent, `405` au lieu de `404` pour les autres méthodes sur `/api/agents/{id}` numérique. Aucune clé ajoutée, renommée ou supprimée sur l'objet agent, aucun code de statut existant modifié.
- **Tickets — Affectation d'un agent et objet `assignee`** : nouvel endpoint `PATCH /api/tickets/{id}/assignee` pour affecter un agent actif à un ticket ou retirer l'affectation, et l'objet ticket renvoyé par tous les endpoints expose désormais l'agent affecté sous la clé `assignee` au lieu d'un `null` fixe.
  - `PATCH /api/tickets/{id}/assignee` (route `ticket_assignee`, `id` numérique) reçoit un objet JSON `{"agentId": int|null}` avec `Content-Type: application/json` ; les clés inconnues du corps sont ignorées. Avec l'`id` d'un agent existant et actif, le ticket est affecté à cet agent et la réponse est `200` avec l'objet ticket complet (`id`, `title`, `description`, `priority`, `status`, `createdAt`, `dueAt`, `assignee`). Réaffecter remplace l'agent précédent ; affecter l'agent déjà en place renvoie le même `200`.
  - `{"agentId": null}` retire l'affectation : `200` avec `"assignee": null`, y compris si le ticket n'avait pas d'agent (aucune recherche d'agent dans ce cas).
  - Ordre des contrôles : le corps est validé avant l'action, puis le ticket est recherché, puis l'agent. Ticket inconnu : `404` `{"error": "Ticket not found"}` (même texte que `PATCH /{id}/status`). Agent inconnu (dont `0` et les entiers négatifs) : `404` `{"error": "Agent not found"}`. Agent inactif : `422` `{"errors": {"agentId": "Agent is not active."}}`. Dans ces trois cas rien n'est modifié ni journalisé.
  - Corps sans clé `agentId` (`{}` ou autres clés seulement) ou `agentId` qui n'est ni un entier ni `null` (`"abc"`, `"5"`, `true`, `1.5`) : `422` `{"errors": {"agentId": "<message>"}}`, jamais une désaffectation silencieuse. Corps non JSON ou vide : `400` ; `Content-Type` autre que JSON : `415`. Toutes ces erreurs sont en `application/json` (`#[MapRequestPayload(acceptFormat: 'json')]` avec `REQUIRE_ALL_PROPERTIES`, rendu par `ApiExceptionListener`).
  - Journalisation : chaque affectation ou désaffectation réussie écrit une ligne `info` `Ticket assignee changed` avec le contexte `{"id": <id ticket>, "assignee": <id agent ou null>}` ; les requêtes refusées ne sont pas journalisées.
  - `Ticket::toArray()` : la valeur de `assignee` devient `{"id": <int>, "name": <string>}` (ces deux clés seulement, ni `email` ni `active`) quand un agent est affecté, `null` sinon. Cette valeur apparaît sur `GET /api/tickets` (chaque élément), `GET /api/tickets/{id}`, `PATCH /api/tickets/{id}/status` et le nouvel endpoint ; `POST /api/tickets` renvoie toujours `null`. Un agent désactivé après affectation reste visible comme `assignee` ; la désactivation ne désaffecte pas.
  - Nouveau fichier `src/Dto/AssignTicketRequest.php` (DTO `final readonly`, propriété `agentId` typée `mixed` avec `#[Assert\Type('int')]`, sans valeur par défaut) ; `TicketController` reçoit `AgentRepository` en dépendance et gagne l'action `assign()`. Aucune migration, aucun changement de schéma (`assignee_id` existe depuis la version 0.2.0) ; `Agent`, `AgentRepository`, `TicketRepository` et la configuration sont inchangés.
  - Appelants existants : `GET/POST /api/tickets`, `GET /api/tickets/{id}`, `PATCH /api/tickets/{id}/status` et `GET /api/stats` conservent leurs codes de statut, enveloppes, clés et corps d'erreur ; la seule différence visible est la valeur de `assignee` pour les tickets affectés.
  - **Impact API** : nouvelle route `PATCH /api/tickets/{id}/assignee` (`200`, `400`, `404`, `415`, `422`). Sur toutes les réponses contenant un objet ticket, la clé `assignee` passe de `null` systématique à `null` ou `{"id", "name"}` ; aucune clé ajoutée, renommée ou supprimée, aucun code de statut existant modifié.
- **Tickets — Filtre SLA dépassé sur la liste** : `GET /api/tickets` accepte un paramètre de requête optionnel `breached` (`true` ou `false`) pour ne renvoyer que les tickets dont l'échéance SLA est dépassée, ou au contraire ceux qui ne le sont pas, en combinaison possible avec le filtre `status`.
  - Définition d'un ticket « dépassé » (URS-002, section 3), évaluée à l'heure serveur au moment de la requête : `status` différent de `closed` **et** `dueAt` non `null` **et** `dueAt` strictement antérieur à l'instant courant. Un ticket `closed` n'est jamais dépassé, quelle que soit son échéance ; un ticket dont `dueAt` vaut `null` (lignes antérieures à la migration de la version 0.2.0) n'est jamais dépassé ; une échéance égale à l'instant courant n'est pas dépassée.
  - `GET /api/tickets?breached=true` renvoie `200` avec `items` limité aux tickets dépassés, triés par `createdAt` DESC puis `id` DESC, et `count` égal au nombre d'éléments ; sans correspondance, `200` `{"items": [], "count": 0}`. `GET /api/tickets?breached=false` renvoie exactement le complément (tickets `closed`, tickets sans `dueAt`, tickets dont `dueAt` n'est pas encore atteint), même tri ; pour un instant donné, les deux listes forment une partition de la liste complète.
  - Combinaison avec `status` (ET logique, paramètres dans un ordre quelconque) : `?status=open&breached=true` renvoie les tickets `open` dépassés ; `?status=closed&breached=true` renvoie toujours `{"items": [], "count": 0}` ; `?status=closed&breached=false` renvoie tous les tickets `closed`.
  - Toute valeur `breached` présente mais différente des chaînes exactes `true` ou `false` (chaîne vide, `1`, `0`, `True`, `TRUE`, `yes`, `no`, `%20true`, `treu`, ou une valeur non scalaire comme `breached[]=true`) renvoie `400` en `application/json` avec exactement `{"error": "Invalid breached", "allowed": ["true", "false"]}` ; la base n'est pas interrogée et aucune page HTML d'erreur n'est produite. `status` est validé avant `breached` : `?status=done&breached=maybe` renvoie le corps `{"error": "Invalid status", ...}` existant.
  - Sans paramètre `breached`, le comportement est inchangé : même liste, même tri, même enveloppe `items` / `count`, même objet ticket (`id`, `title`, `description`, `priority`, `status`, `createdAt`, `dueAt`, `assignee`), avec ou sans `?status=`. Aucune clé `breached` n'est ajoutée à l'objet ticket. `POST /api/tickets`, `GET /api/tickets/{id}`, `PATCH /api/tickets/{id}/status`, `PATCH /api/tickets/{id}/assignee`, `/api/agents*` et `GET /api/stats` ne sont pas modifiés.
  - Dépôt `App\Repository\TicketRepository` : nouvelle méthode `withBreached(QueryBuilder, bool $breached, \DateTimeImmutable $now): QueryBuilder`, seul emplacement du prédicat de dépassement (`t.status <> :closedStatus AND t.dueAt IS NOT NULL AND t.dueAt < :now` pour `true`, `t.status = :closedStatus OR t.dueAt IS NULL OR t.dueAt >= :now` pour `false`, paramètre `now` lié en `Types::DATETIME_IMMUTABLE`), empilable via `andWhere` avant ou après `withStatus()` ; l'horloge est toujours passée en argument, jamais lue par la méthode. `findNewestFirst(?string $status = null, ?bool $breached = null, ?\DateTimeImmutable $now = null)` gagne deux paramètres optionnels (`now` à défaut `new \DateTimeImmutable()`) ; les appels `findNewestFirst()` et `findNewestFirst($status)` existants renvoient les mêmes listes. `createNewestFirstQueryBuilder()`, `withStatus()`, `findAllNewestFirst()` et `countByStatus()` sont inchangés. Aucune migration, aucun changement de schéma, d'entité, de configuration ni de dépendance.
  - **Impact API** : nouveau code de réponse `400` (`application/json`, corps `error` + `allowed`) sur `GET /api/tickets` lorsque `breached` est fourni avec une valeur invalide ; auparavant ce paramètre était ignoré et la liste complète (ou filtrée par `status`) renvoyée en `200`. Aucun changement de forme pour les réponses `200`.
- **Rapports — Rapport SLA par priorité** : nouvel endpoint `GET /api/reports/sla` qui renvoie, pour chaque priorité, le nombre total de tickets, le nombre de tickets dont l'échéance SLA est dépassée et le taux de dépassement en pourcentage.
  - `GET /api/reports/sla` (route `report_sla`, sans paramètre ni corps) renvoie `200` en `application/json` avec exactement deux clés, dans cet ordre : `generatedAt` (instant d'évaluation à l'heure serveur, chaîne ISO 8601 `DATE_ATOM`, même format que `createdAt` / `dueAt`) et `priorities` (tableau JSON, jamais un objet indexé par priorité).
  - Chaque élément de `priorities` porte exactement les clés `priority` (chaîne), `total` (entier), `breached` (entier) et `breach_rate` (nombre), dans cet ordre. Les trois priorités connues `low`, `normal`, `high` sont toujours présentes, dans cet ordre, même avec `total` à `0` (`{"priority": "low", "total": 0, "breached": 0, "breach_rate": 0.0}`).
  - Définitions : `total` compte tous les tickets de la priorité, quel que soit leur statut ; `breached` compte ceux qui sont « dépassés » au sens de la version précédente (`status` différent de `closed` **et** `dueAt` non `null` **et** `dueAt` antérieur à l'instant courant), via le même prédicat que `GET /api/tickets?breached=true` ; un seul instant `now` sert à toutes les priorités et à `generatedAt`. `breach_rate` vaut `breached / total * 100` arrondi à une décimale (`round($x, 1)`, par exemple `33.3`, `66.7`, `16.7`, `100.0`) et `0.0` quand `total` est `0` (aucune division).
  - `breach_rate` est toujours encodé comme un nombre JSON avec partie décimale (`0.0`, `50.0`, `100.0`, jamais `0`, `50` ni `"50.0"`) : la réponse est construite avec `JSON_PRESERVE_ZERO_FRACTION` ajouté aux options d'encodage par défaut de `JsonResponse`, de sorte que `json_decode()` côté client renvoie un flottant pour chaque taux.
  - Table vide : `200` avec les trois entrées à zéro (`priorities` contient exactement 3 éléments), jamais `500`, `null` ni `NaN`.
  - Priorités inconnues (par exemple `urgent` posté par le simulateur de trafic) : les tickets dont `priority` n'est pas dans `Ticket::PRIORITIES` ne sont pas ignorés mais agrégés, quelle que soit leur valeur réelle, dans une entrée supplémentaire `{"priority": "other", ...}` calculée avec les mêmes règles et placée en dernière position ; cette entrée n'apparaît que si son `total` est au moins `1`. La somme des `total` est donc toujours égale au nombre de lignes de `ticket`, et la somme des `breached` égale au `count` de `GET /api/tickets?breached=true` au même instant.
  - Toute chaîne de requête est ignorée (`?breached=maybe`, `?status=done`, `?priority[]=low`, `?now[a]=1`) : même `200` et mêmes `priorities` qu'un appel nu ; aucun `400`, `500` ni page HTML. `POST`, `PUT`, `PATCH` et `DELETE` sur `/api/reports/sla` renvoient `405` en `application/json` avec une clé `error` et un en-tête `Allow` contenant `GET` (rendu par l'`ApiExceptionListener` existant).
  - Nouveau service `App\Service\SlaReport` (autowiré, constructeur sur `TicketRepository`, méthode `generate(?\DateTimeImmutable $now = null): array`) qui calcule le rapport en deux requêtes groupées (totaux, puis dépassés) sans charger d'entité ; `$now` à défaut `new \DateTimeImmutable()`, injectable pour figer l'horloge en test. Nouveau contrôleur invocable `App\Controller\SlaReportController` sans comptage ni arrondi.
  - Dépôt `App\Repository\TicketRepository` : nouvelle méthode `countByPriority(?bool $breached = null, ?\DateTimeImmutable $now = null): array` (`priority => int`, une seule requête `SELECT t.priority, COUNT(t.id) ... GROUP BY t.priority` sur `createQueryBuilder('t')`, `withBreached()` appliqué quand `$breached` n'est pas `null`) ; table vide ou aucune correspondance : `[]`. `withBreached()`, `findNewestFirst()`, `createNewestFirstQueryBuilder()`, `withStatus()`, `findAllNewestFirst()` et `countByStatus()` sont inchangés.
  - Appelants existants : `GET /api/stats` conserve exactement ses cinq clés (`total`, `open`, `in_progress`, `closed`, `closed_ratio`) et son comportement ; `GET /api/tickets` (avec ou sans `status` / `breached`), `POST /api/tickets`, `GET /api/tickets/{id}`, `PATCH /api/tickets/{id}/status`, `PATCH /api/tickets/{id}/assignee` et `/api/agents*` gardent leurs codes de statut et leurs formes JSON ; aucune clé ajoutée ni retirée de l'objet ticket. Aucune migration, aucun changement de schéma, d'entité, de configuration ni de dépendance.
  - **Impact API** : nouvelle route `GET /api/reports/sla` (`200`, `405` pour les autres méthodes). Aucune réponse existante modifiée.

**Corrections de bugs**

- **Tickets — Création validée, `404` JSON à la consultation, statistiques sur table vide** : trois erreurs `500` de l'API sont corrigées (`POST /api/tickets` avec un corps incomplet, `GET /api/tickets/{id}` sur un identifiant inconnu, `GET /api/stats` sans aucun ticket), le corps de `POST /api/tickets` est désormais validé et toute priorité hors de `low`, `normal`, `high` est refusée au lieu d'être stockée.
  - `POST /api/tickets` est lié par `#[MapRequestPayload(acceptFormat: 'json')]` au nouveau DTO `App\Dto\CreateTicketRequest` (`final readonly`, propriétés `title`, `description`, `priority` de type `string` avec `''` par défaut) ; le `json_decode()` manuel de `create()` est supprimé. Contraintes : `title` obligatoire, non vide après `trim`, 120 caractères maximum (longueur de la colonne) ; `description` obligatoire, non vide après `trim` ; `priority` obligatoire et exactement l'une des valeurs de `Ticket::PRIORITIES` (`low`, `normal`, `high`). Les clés inconnues du corps sont ignorées ; les valeurs sont stockées telles quelles, sans rognage.
  - Validation (`422`, `application/json`, corps `{"errors": {"<champ>": "<message>"}}`, une entrée par champ en faute seulement, messages Symfony par défaut en anglais) : `priority` absente, `null`, non chaîne, vide ou hors liste (`urgent`, `High`, `LOW`, `123`) ; `title` absent, `null`, non chaîne, vide ou blanc, ou de plus de 120 caractères ; `description` absente, `null`, non chaîne, vide ou blanche ; un corps `{}` renvoie les trois clés. Rien n'est persisté dans ces cas. Auparavant, un corps sans l'une des trois clés provoquait un `500` (`Undefined array key`) et n'importe quelle chaîne était acceptée comme priorité.
  - Corps non JSON (`{not json`) ou vide : `400` ; `Content-Type` autre que JSON (par exemple `text/plain`) : `415` ; dans les deux cas `application/json` avec `{"error": "<message>"}`, rendu par l'`ApiExceptionListener` existant, comme sur `/api/agents`. Jamais de page HTML, jamais de `500`.
  - Décision sur `urgent` (`requests/002-urgent-priority.md`) : la valeur n'est pas ajoutée à `Ticket::PRIORITIES` ni à `SLA_TARGET_HOURS` (elle recevrait la cible `normal` de 24 h, moins stricte que `high`) ; `POST /api/tickets` avec `"priority": "urgent"` renvoie `422` sur `priority`. Les tickets déjà stockés avec une priorité hors liste sont conservés et toujours servis tels quels par `GET /api/tickets` et `GET /api/tickets/{id}` ; la demande 002 reste ouverte et devra préciser une cible SLA.
  - `GET /api/tickets/{id}` avec un `id` numérique sans ticket correspondant (dont `0`) renvoie `404` avec exactement `{"error": "Ticket not found"}` (même texte que `PATCH /{id}/status` et `PATCH /{id}/assignee`) au lieu d'un `500` (`toArray()` sur `null`) ; la réponse est construite par l'action `show()`, sans ligne de log. Un `id` non numérique garde le `404` JSON de l'écouteur ; un `id` connu renvoie toujours `200` avec l'objet ticket.
  - `GET /api/stats` : `TicketStats::summary()` renvoie `closed_ratio` à `0` lorsque `total` vaut `0` (`0 === $total ? 0.0 : round(...)`), plus de `DivisionByZeroError` sur une table vide (`requests/003-dashboard-blank-on-monday.md`) ; les cinq clés `total`, `open`, `in_progress`, `closed`, `closed_ratio`, leur ordre et l'arrondi à une décimale sont inchangés avec des tickets ; `StatsController` n'est pas modifié.
  - Trafic standard (URS-002, section 6) : `app:simulate-traffic --reset` produit `HTTP 200: 6`, `HTTP 201: 2`, `HTTP 404: 1`, `HTTP 422: 3`, aucun `5xx` et aucune ligne `CRITICAL` dans `var/log/dev.log` ; le scénario de `SimulateTrafficCommand` n'est pas modifié et sert de recette. Journal d'audit (URS-N-01) : les lignes `info` `Ticket assignee changed` (`{"id", "assignee"}`) et `Agent activation changed` (`{"id", "active"}`) sont inchangées et couvertes par un test de balayage supplémentaire.
  - Appelants existants : une création valide renvoie toujours `201` avec l'objet ticket à huit clés (`id`, `title`, `description`, `priority`, `status`, `createdAt`, `dueAt`, `assignee`), `status` `open`, `assignee` `null`, `dueAt` selon la priorité, et la ligne `info` `Ticket created` ; `GET /api/tickets` (filtres `status` et `breached`), `PATCH /api/tickets/{id}/status` (corps `422` `{"error": "Invalid status", "allowed": [...]}` et `404` inchangés), `PATCH /api/tickets/{id}/assignee`, `/api/agents*` et `GET /api/reports/sla` conservent leurs codes et leurs corps. Aucune migration, aucun changement de schéma, d'entité (`Ticket.php` non modifié), de configuration ni de dépendance ; `ApiExceptionListener` reste limité aux `HttpExceptionInterface`.
  - **Impact API** : `POST /api/tickets` renvoie désormais `422` `{"errors": {"priority": "<message>"}}` pour toute priorité hors de `low`, `normal`, `high` (notamment `urgent`), là où la valeur était auparavant acceptée et stockée avec un `201` ; un corps incomplet (`422` `{"errors": {...}}`), non JSON (`400`) ou de `Content-Type` non JSON (`415`) remplace un `500`. `GET /api/tickets/{id}` inconnu : `404` `{"error": "Ticket not found"}` au lieu de `500`. `GET /api/stats` sur table vide : `200` avec les cinq clés à `0` au lieu de `500`. Aucune clé ajoutée, renommée ou supprimée sur les réponses `200` et `201`.
