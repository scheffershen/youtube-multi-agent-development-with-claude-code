- **Agents — Création et liste des agents** : deux nouveaux endpoints, `POST /api/agents` pour créer un agent (e-mail unique) et `GET /api/agents` pour lister les agents, actifs en premier.
  - `POST /api/agents` reçoit un objet JSON `{"name": string, "email": string, "active"?: bool}` avec `Content-Type: application/json` et renvoie `201` avec l'objet agent `{"id", "name", "email", "active"}` (clés dans cet ordre, aucune autre clé, pas d'en-tête `Location`). `active` vaut `true` par défaut ; `name` et `email` sont stockés tels quels (ni rognage ni passage en minuscules) ; les clés inconnues du corps sont ignorées.
  - Validation (`422`, `application/json`, corps `{"errors": {"<champ>": "<message>"}}`, un message par champ en faute, premier message de violation) : `name` obligatoire, non vide après `trim`, 120 caractères maximum ; `email` obligatoire, non vide après `trim`, adresse syntaxiquement valide, 180 caractères maximum ; `active` doit être un booléen s'il est fourni. Rien n'est persisté dans ces cas. Les messages par défaut de Symfony sont en anglais (aucun traducteur installé).
  - Unicité de l'e-mail : un `email` déjà présent (comparaison exacte, sensible à la casse, comme l'index unique) renvoie `422` avec exactement `{"errors": {"email": "An agent with this email already exists."}}` ; le contrôle passe par `AgentRepository::findOneBy(['email' => ...])` avant l'insertion, et une `UniqueConstraintViolationException` au `flush()` (insertion concurrente) est rattrapée et renvoie le même corps `422`, jamais un `500`.
  - Corps non JSON ou vide : `400` ; `Content-Type` autre que JSON (par exemple `text/plain`) : `415` (`#[MapRequestPayload(acceptFormat: 'json')]`). Dans les deux cas la réponse est en `application/json` avec `{"error": "<message>"}`.
  - `GET /api/agents` renvoie `200` et `{"items": [<agent>, ...], "count": n}`, `count` égal au nombre d'éléments ; tri `active` DESC puis `id` ASC (agents actifs d'abord, chaque groupe par ordre de création) ; sans agent, exactement `{"items": [], "count": 0}`. Les paramètres de requête sont ignorés (ni filtre ni pagination).
  - Dépôt `App\Repository\AgentRepository` : nouvelle méthode `findActiveFirst(): list<Agent>` (`findBy([], ['active' => 'DESC', 'id' => 'ASC'])`). Nouveaux fichiers `src/Controller/AgentController.php` (routes `agent_list`, `agent_create`), `src/Dto/CreateAgentRequest.php` (DTO `final readonly`, contraintes `#[Assert\...]`) et `src/EventListener/ApiExceptionListener.php`. Aucune migration ; l'entité `Agent` et le schéma sont inchangés.
  - Rendu JSON des erreurs HTTP sous `/api/` : l'écouteur `ApiExceptionListener` (`KernelEvents::EXCEPTION`) convertit en JSON toute exception `HttpExceptionInterface` levée pour un chemin commençant par `/api/` (`{"errors": {...}}` si l'exception enveloppe une `ValidationFailedException`, `{"error": "<message>"}` sinon, code de statut et en-têtes de l'exception conservés). Les autres exceptions ne sont pas touchées et les réponses construites par les contrôleurs ne sont pas modifiées.
  - Dépendances : `symfony/property-access` et `symfony/property-info` ajoutés à `composer.json` (requis par `#[MapRequestPayload]` sur un DTO) ; recette Flex `config/packages/property_info.yaml` (`framework.property_info.with_constructor_extractor: true`).
  - Appelants existants : `GET/POST /api/tickets`, `GET /api/tickets/{id}`, `PATCH /api/tickets/{id}/status` (toujours `422` `{"error": "Invalid status"}` sur statut invalide) et `GET /api/stats` conservent leurs codes de statut et leurs corps JSON.
  - **Impact API** : deux nouvelles routes `GET /api/agents` (`200`) et `POST /api/agents` (`201`, `400`, `415`, `422`). Effet de bord de l'écouteur : une route inconnue sous `/api/` renvoie désormais son `404` en `application/json` `{"error": "<message>"}` au lieu de la page HTML d'erreur du noyau ; aucun code de statut ni forme de réponse des endpoints existants ne change.
