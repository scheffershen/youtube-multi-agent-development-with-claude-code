- **Tickets — Filtre SLA dépassé sur la liste** : `GET /api/tickets` accepte un paramètre de requête optionnel `breached` (`true` ou `false`) pour ne renvoyer que les tickets dont l'échéance SLA est dépassée, ou au contraire ceux qui ne le sont pas, en combinaison possible avec le filtre `status`.
  - Définition d'un ticket « dépassé » (URS-002, section 3), évaluée à l'heure serveur au moment de la requête : `status` différent de `closed` **et** `dueAt` non `null` **et** `dueAt` strictement antérieur à l'instant courant. Un ticket `closed` n'est jamais dépassé, quelle que soit son échéance ; un ticket dont `dueAt` vaut `null` (lignes antérieures à la migration de la version 0.2.0) n'est jamais dépassé ; une échéance égale à l'instant courant n'est pas dépassée.
  - `GET /api/tickets?breached=true` renvoie `200` avec `items` limité aux tickets dépassés, triés par `createdAt` DESC puis `id` DESC, et `count` égal au nombre d'éléments ; sans correspondance, `200` `{"items": [], "count": 0}`. `GET /api/tickets?breached=false` renvoie exactement le complément (tickets `closed`, tickets sans `dueAt`, tickets dont `dueAt` n'est pas encore atteint), même tri ; pour un instant donné, les deux listes forment une partition de la liste complète.
  - Combinaison avec `status` (ET logique, paramètres dans un ordre quelconque) : `?status=open&breached=true` renvoie les tickets `open` dépassés ; `?status=closed&breached=true` renvoie toujours `{"items": [], "count": 0}` ; `?status=closed&breached=false` renvoie tous les tickets `closed`.
  - Toute valeur `breached` présente mais différente des chaînes exactes `true` ou `false` (chaîne vide, `1`, `0`, `True`, `TRUE`, `yes`, `no`, `%20true`, `treu`, ou une valeur non scalaire comme `breached[]=true`) renvoie `400` en `application/json` avec exactement `{"error": "Invalid breached", "allowed": ["true", "false"]}` ; la base n'est pas interrogée et aucune page HTML d'erreur n'est produite. `status` est validé avant `breached` : `?status=done&breached=maybe` renvoie le corps `{"error": "Invalid status", ...}` existant.
  - Sans paramètre `breached`, le comportement est inchangé : même liste, même tri, même enveloppe `items` / `count`, même objet ticket (`id`, `title`, `description`, `priority`, `status`, `createdAt`, `dueAt`, `assignee`), avec ou sans `?status=`. Aucune clé `breached` n'est ajoutée à l'objet ticket. `POST /api/tickets`, `GET /api/tickets/{id}`, `PATCH /api/tickets/{id}/status`, `PATCH /api/tickets/{id}/assignee`, `/api/agents*` et `GET /api/stats` ne sont pas modifiés.
  - Dépôt `App\Repository\TicketRepository` : nouvelle méthode `withBreached(QueryBuilder, bool $breached, \DateTimeImmutable $now): QueryBuilder`, seul emplacement du prédicat de dépassement (`t.status <> :closedStatus AND t.dueAt IS NOT NULL AND t.dueAt < :now` pour `true`, `t.status = :closedStatus OR t.dueAt IS NULL OR t.dueAt >= :now` pour `false`, paramètre `now` lié en `Types::DATETIME_IMMUTABLE`), empilable via `andWhere` avant ou après `withStatus()` ; l'horloge est toujours passée en argument, jamais lue par la méthode. `findNewestFirst(?string $status = null, ?bool $breached = null, ?\DateTimeImmutable $now = null)` gagne deux paramètres optionnels (`now` à défaut `new \DateTimeImmutable()`) ; les appels `findNewestFirst()` et `findNewestFirst($status)` existants renvoient les mêmes listes. `createNewestFirstQueryBuilder()`, `withStatus()`, `findAllNewestFirst()` et `countByStatus()` sont inchangés. Aucune migration, aucun changement de schéma, d'entité, de configuration ni de dépendance.
  - **Impact API** : nouveau code de réponse `400` (`application/json`, corps `error` + `allowed`) sur `GET /api/tickets` lorsque `breached` est fourni avec une valeur invalide ; auparavant ce paramètre était ignoré et la liste complète (ou filtrée par `status`) renvoyée en `200`. Aucun changement de forme pour les réponses `200`.
